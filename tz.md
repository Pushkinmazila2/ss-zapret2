### Путь трафика (продолжение раздела 3)

1. Внешний клиент SOCKS5 -> ss-local -> loopback Shadowsocks ss-server -> адрес назначения.
2. Клиент Shadowsocks -> ss-server -> адрес назначения.
3. Выбранный исходящий трафик -> netfilter/NFQUEUE -> обработка стратегиями nfqws2.
4. В режиме пула (pool mode) соединениям присваиваются метки очередей (queue marks), а связанный входящий трафик направляется в соответствующую очередь.

На данный момент при запуске проверяются пять обязательных переменных окружения, копируются недостающие ресурсы верхнего уровня Lua/fake/example (без перезаписи существующих записей), запускается апстрим-модуль zapret2, поднимается панель управления, после чего запускаются оба процесса прокси с включенным UDP. Логи сервера перенаправляются в файл среды выполнения с добавлением префиксов. При выключении система пытается остановить zapret2 и дочерние процессы. Панель автоматически запускает пул, если находит `NFQWS2_ENABLE=0` в конфигурации.

**Целевой жизненный цикл:** валидировать конфигурацию и доступные возможности системы перед внесением изменений; приводить систему строго к одному рабочему режиму; запускать и проверять собственные дочерние процессы; применять проверенные правила файрвола; объявлять о готовности системы только после того, как прокси и состояние стратегий станут пригодными для использования. Корректно обрабатывать сигналы SIGTERM/SIGINT, очищать за собой дочерние процессы, ограничивать время завершения работы и удалять только собственные ресурсы. Отсутствие необязательных компонентов диагностики должно приводить к переходу в режим ограниченной (деградировавшей) диагностики, а не к ложному статусу «здоров» или сбою в работе прокси.

## 4. Функциональные требования

### FR-01 — Развертывание и прокси-сервис

- Сохранить возможность настройки порта Shadowsocks, пароля, метода шифрования, таймаута сокета, уровня логирования (verbosity) и порта SOCKS5.
- В примерах сейчас используются порты 8388/1080 и шифрование `chacha20-ietf-poly1305`; дефолтный пароль из примера не является безопасным для продакшена.
- Держать привязки TCP и UDP явными. По умолчанию привязывать порты прокси и панели управления к локальной петле (loopback/localhost); документировать возможность осознанного открытия портов наружу и удаленного администрирования с аутентификацией.
- Сохранить изоляцию через Docker bridge. Внешняя сеть приложений должна быть опциональной, а не обязательным условием для чистой установки.
- Сохранить монтирование расширений и переопределение хостов оператора через директиву Compose `extra_hosts`.
- Проверка работоспособности (Health check) должна различать: активность процессов (liveness), готовность локальных слушателей портов, готовность файрвола/очередей и наличие внешнего интернет-соединения. Сбой теста внешнего интернета сам по себе не должен вызывать бесконечный неконтролируемый цикл перезапуска контейнера.

### FR-02 — Конфигурация и классический режим

**Реализовано:** чтение сырого файла конфигурации и извлечение `NFQWS2_OPT`; замена этого блока с сохранением остальных строк и комментариев; создание резервной копии предыдущего конфига в `.bak`; опциональный перезапуск демонов; применение именованного пресета; чтение текста бэкапа; перезапуск апстрим-демонов.

**Целевое решение:**

- Принимать существующие однострочные и многострочные блоки в кавычках, а также блоки в стиле пресетов репозитория через протестированный парсер. Сохранять несвязанные настройки и комментарии.
- Валидировать конфигурацию перед сохранением; сериализовать параллельные записи; использовать атомарную замену файлов там, где это поддерживается структурой развертывания; явно обрабатывать сценарии с монтированием отдельных файлов (single-file bind mounts), где замена через переименование неприменима.
- Разделять сохраненную конфигурацию и успешно примененную конфигурацию. Корректно возвращать ошибки перезапуска; поддерживать откат (rollback) к последней известной рабочей ревизии.
- Относиться к конфигурации апстрим-скриптов и Lua-файлам как к привилегированному контенту оператора. Никогда не выполнять код из ненадежного импортируемого текста. Безопасно сериализовать разрешенные значения; отклонять шелл-инъекции, ошибки экранирования и непредусмотренные исполняемые конструкции.
- Классический режим (Classic mode) использует один демон, управляемый апстримом. Режим пула (Pool mode) отключает апстрим-демон и конфликтующие кастомные хуки. Переключение режимов должно быть транзакционным и восстанавливать предыдущий режим в случае сбоя.
- Параметр `mode="single"` принимается в текущем коде, но не имеет под собой отдельного рабочего пути логики. Необходимо явно определить семантику однослотового пула, вместо того чтобы молча принимать неэффективные настройки.

### FR-03 — Каталог стратегий и импорт

**Реализовано:** сортированный поиск файлов `.conf`; имя стратегии берется из имени файла; описание — из первого комментария; извлечение сырых опций и флага `has_nfqws`; импорт JSON в сгенерированные файлы пресетов. Пустые или устаревшие блоки опций исключаются из автоматического выбора пула.

Контракт импорта:
```json
{
  "domain": "example.com",
  "name_prefix": "example",
  "strategies": [
    {
      "args": "--filter-tcp=443 --filter-l7=tls --lua-desync=multisplit:pos=2",
      "protocol": "tcp",
      "success_rate": 0.95,
      "median_latency_ms": 120,
      "median_speed_kbps": 5000
    }
  ]
}
```

Устаревшие алиасы ввода: `prefix` на верхнем уровне; `nfqws_opt` внутри конкретной стратегии. Если `prefix` отсутствует, система использует имя домена, заменяя точки на нижние подчеркивания, а затем импортирует данные. Текущий формат именования: `<prefix>_001.conf` и т.д. Текущий импорт автоматически добавляет фильтры `TCP/443` и `TLS`, если не заданы фильтры TCP или UDP, и помещает метаданные в комментарий. Возвращает имена сохраненных элементов и ошибки по каждому пункту.

**Целевые исправления:** валидировать типы данных, размеры, количество, имена, корректность путей (path containment), числовые метаданные, синтаксис поддерживаемого движка и конфликты имен файлов. Никогда не перезаписывать файлы втихую. Держать валидацию импорта отдельно от его активации. Не подставлять автоматически TCP для явных UDP-стратегий. Сохранять метаданные как структурированные данные, а сырые опции — как текст без потерь. Отклонять или явно помечать неподдерживаемые устаревшие пресеты; не пытаться на ходу выдумывать конвертацию из старого формата `DESYNC_*`.

Встроенный каталог: `disorder.conf` использует устаревшие поля без `NFQWS2_OPT`; `nfqws-youtube.conf` содержит профили HTTP, YouTube TLS, Discord-update TLS, generic TLS и QUIC. Последний — единственный встроенный пресет, пригодный для пула. Таким образом, дефолтный размер пула, равный трем, не означает, что в системе есть три полезные встроенные стратегии.

### FR-04 — Управление пулом и воркерами

- Поддерживать до 10 обычных слотов, каждый из которых имеет стабильный ID слота, номер очереди, стратегию, опции, PID, время запуска, статус здоровья (`unknown/healthy/unhealthy`), активность процесса и состояние включения в маршрутизацию.
- Для совместимости выделение очередей начинается с 300; обычные слоты стандартно используют формулу `300 + индекс`. Временные кандидаты используют незанятые очереди внутри зарезервированного диапазона. Запретить переполнение диапазона и коллизии номеров.
- Поддерживать включение/выключение, добавление/удаление, ручную замену стратегии в слоте, фоновую проверку и восстановление через watchdog.
- Текущий целевой размер по умолчанию равен трем, что ограничено доступными подходящими стратегиями и максимальным числом слотов. В целевой архитектуре система должна корректно пересчитывать желаемый размер после изменения настроек и правильно распределять свободные ID после удаления слотов.
- Запускать `nfqws2` с явными массивами аргументов, номерами очередей, метками `fwmark`, под непривилегированным пользователем (сейчас это `nobody`) и передавать апстрим-скрипты инициализации Lua (`library/antidpi/auto`). Сохранять поддержку `NFQWS2_EXTRA_ARGS`, но валидировать их на предмет перезаписи зарезервированных опций.
- Захватывать ограниченный по объему stdout/stderr для каждого слота и логировать события жизненного цикла. Существующий механизм пытается выполнить запуск три раза с короткими задержками; для замены воркеров и watchdog требуется ограничение экспоненциального отката (bounded backoff) и наблюдаемые состояния сбоя.
- Процесс, который просто не упал сразу после старта, еще не считается проверенной и эффективной стратегией. Избегать безусловного дебаг-логирования в продакшене.

### FR-05 — Файрвол и connection affinity (привязка соединений)

**Реализованное намерение:** цепочка `ZAPRET_POOL` в таблице `mangle` восстанавливает младшие 16 бит метки соединения (`connmark`); уже размеченный трафик отправляется в свою очередь; неразмеченный трафик случайно распределяется в равных долях между слотами, и метка выбранной очереди сохраняется в `connmark`. Входящий трафик TCP/UDP восстанавливает ту же метку. Все пакеты, подходящие под критерии, а не только первые N пакетов, участвуют в обработке. Метка `DESYNC_MARK` предотвращает образование петель маршрутизации. Списки `ipset` определяют целевые направления TCP/UDP и списки исключений `nozapret`. Правила очередей используют флаг `--queue-bypass`.

**Целевые инварианты:**

1. Только один компонент системы управляет правилами пула. Убрать или изолировать устаревший кастомный хук, чьи правила расходятся с Python-реализацией.
2. Обновлять правила атомарно или с проверенным планом отката. Контролировать ошибки выполнения команд, использовать ограниченные таймауты и ожидания блокировок файрвола.
3. Никогда не очищать встроенную цепочку `INPUT` целиком и не удалять чужие очереди/правила. Использовать собственные изолированные цепочки и правила явного перехода (`jump`) для обоих направлений трафика.
4. Сохранять сторонние метки пакетов за пределами выделенной маски; держать диагностические биты и биты защиты от петель отдельно от ID очереди.
5. Никогда не направлять трафик в неготовую очередь. Явно определить поведение системы, когда все кандидаты вышли из строя: настраиваемый режим пропуска трафика без обработки (fail-open) или полная блокировка (fail-closed) с видимым отображением в статусе; нельзя молча возвращать в работу заведомо нерабочую стратегию.
6. При удалении слота или замене его процесса должно быть четко определено, что происходит с текущими размеченными потоками трафика. Предпочтительно давать старым воркерам доработать существующие соединения (drain) в рамках жесткого таймаута, направляя все новые потоки в новые очереди. Не гарантировать сохранение сессий, если старый воркер или его состояние не могут быть удержаны.
7. Маршрутизация IPv6 должна строго следовать настроенной политике IPv6. Отсутствие списков ipset не должно приводить к неконтролируемому расширению перехвата или обходу обязательных исключений.
8. Изоляция диагностических зондов (probes) должна выбирать исключительно тестовые потоки данных и никогда не перенаправлять весь клиентский трафик в тестовую очередь.

### FR-06 — Проверки связности, выбор и ротация

**Текущее поведение:** периодический цикл проверки/watchdog; интервал по умолчанию — 60 секунд; порог срабатывания — два сбоя подряд; номинальное время стабилизации (settle) — 6 секунд; тестовый URL по умолчанию — `https://youtube.com`. Проверка всего пула запускает `curl HEAD` через `socks5h` и принимает коды ответов HTTP 2xx/3xx при успешном коде завершения процесса. В случае успеха все живые слоты помечаются как исправные («здоровые»). В случае сбоя тестируются только те слоты, которые уже находятся под подозрением. Изолированный тест временно перенаправляет широкий поток трафика в цепочке `POSTROUTING`. При замене система исключает старый слот, пробует до трех теневых кандидатов (shadow candidates), после чего заменяет или заново включает слот. Теневой кандидат на данный момент считается успешным после фиксации двух пакетов или одного успешного общего `curl` для пула; ни то, ни другое не доказывает эффективность конкретного кандидата. Если все кандидаты терпят неудачу, старая неисправная стратегия возвращается в маршрутизацию.

**Целевое решение:**

- Реализовать явные переходы между состояниями: `disabled` (отключен) / `starting` (запуск) / `idle` (простой) / `checking` (проверка) / `replacing` (замена) / `healthy` (исправен) / `degraded` (деградация) / `stopping` (остановка) / `error` (ошибка) под управлением единого сериализованного координатора изменений.
- Доступность всего пула в целом не является доказательством того, что работает каждый отдельный его участник. Необходимо вести сбор свидетельств по каждому слоту с фиксацией метки времени, области видимости, адреса назначения и причины сбоя.
- Тестировать кандидатов с помощью трафика, жестко привязанного (pinned) именно к проверяемому кандидату; валидировать ответ на уровне приложения и, опционально, фиксацию непрерывной передачи данных. Факт прибытия сетевого пакета сам по себе не означает успех.
- Если проверка пула завершается сбоем при отсутствии предварительно подозреваемых слотов, следует назначать ограниченную по времени диагностику слотов, а не возвращать статус успешной работы.
- Разделять сценарии восстановления после падения процесса, сетевые сбои связности, подозрения на блокировку сессии (cut) и ротацию по инициативе оператора.
- Сохранять работоспособные слоты во время проведения диагностики, избегать наложения проверок/ротаций друг на друга, а также ограничивать уровень параллелизма и таймауты.
- При подтверждении неисправности слота оперативно исключать его из распределения новых соединений; выбирать диверсифицированных кандидатов и публиковать состояние деградации до тех пор, пока замена не пройдет тесты. Опциональная быстрая замена может использовать уже валидированный резервный слот (standby), а не неоттестированного кандидата с ложной меткой «здоров».
- Держать включенной по умолчанию ротацию, триггером которой выступает разрыв сессии (cut-triggered rotation); сохранять 30-секундный период охлаждения (cooldown) ротации, настраиваемое временное окно жизненного цикла и подтверждение сброса. Фиксировать причины, по которым триггер был пропущен, подавлен или взят в обработку.
- Не заявлять о гарантированном отсутствии даунтайма (zero-downtime) для уже существующих сессий. Измерять скорость восстановления новых соединений отдельно от выживаемости текущих потоков.

### FR-07 — Семейства стратегий и адаптивные оценки (scores)

**Реализовано:** эвристическая классификация устаревших режимов `--dpi-desync` на семейства сегментации, фейков, фрагментации IP, расширений IPv6 и TCP-состояний; опциональные компоненты обмана (fooling), TTL, фейковой полезной нагрузки (fake-payload), позиции разделения (split-position) и L7-компоненты. Неизвестные режимы классифицируются как `other`. Оценки жестко ограничиваются диапазоном `[-20, 20]`; успех дает `+1`, сбой `-2`, применяется затухание выбора (selection decay) с коэффициентом `x0.98`; семейство, подозреваемое в попадании под блокировку «на лету» (live-cut), получает `-3` и дефолтный период охлаждения в 600 секунд. При ранжировании первыми идут незатронутые семейства, затем учитывается оценка семейства, затем — оценка конкретной стратегии. Пакеты стратегий диверсифицируются по разным семействам перед тем, как система выберет «родственные» варианты (siblings). Показатель опасности (hazard) рассчитывается как отношение зафиксированных сбоев/блокировок к общему числу исходов; он не является откалиброванной вероятностью.

**Целевое решение:** классифицировать современный синтаксис `--lua-desync` и множественные профили, а не только устаревший синтаксис. Одна стратегия может содержать несколько техник и областей применения. Возвращать каноническую классификацию с сервера на сторону UI; устранить конкурирующую классификацию, выполняемую на стороне браузера. Обеспечить персистентность ID событий и ревизий оценок; детерминированное воспроизведение (replay) должно в точности воссоздавать живые оценки, периоды охлаждения и затухание. Сохранять исходные свидетельства и контекст; не наказывать все семейство целиком на основании одного лишь слабо подтвержденного наблюдения в состоянии простоя. Состояние отсутствия истории должно отличаться от зафиксированной нулевой оценки.

### FR-08 — Монитор сбросов сессий и обнаружение разрывов сессий (session-cut)

**Реализованный монитор сбросов:** осуществляет чтение конца лога (tail) сервера Shadowsocks, подсчитывает соотношение событий `Connection reset by peer` к `close a connection` в рамках 60-секундного скользящего окна при минимуме в 5 событий; триггер срабатывает при коэффициенте деградации `>=0.4`. Система сохраняет итоговые показатели и время последнего сброса; активация происходит при переходе в состояние деградации; метки времени сбросов передаются в трекер. Размер буфера ограничен 500 событиями.

**Реализованный трекер:** каждые две секунды опрашивает `/proc/net/tcp` и `/proc/net/tcp6` на предмет исходящих удаленных соединений на порт 443 со статусом `ESTABLISHED` (исключая локальные порты сервиса). Несмотря на название `yt_active`, он не идентифицирует домены YouTube как таковые. Трекер отслеживает суммарный период времени, в течение которого существует хотя бы один подходящий сокет. После 5 секунд отсутствия подходящих сокетов он проверяет 30–60-секундное окно длительности сессий и, опционально, недавнее подтверждение сброса (10-секундное окно плюс задержка опроса). Обнаружение простоя (idle) сравнивает заполненность очередей сокетов `tx/rx`: требуется 5 неизменных тактов (ticks), не менее 15 секунд времени жизни сокета и номинальный порог простоя в 10 секунд.

**Исторический функционал:** классификация FIN-vs-RST для каждого потока и обнаружение эпидемий (4 быстрых сброса со смертельным исходом за 60 секунд) описаны в `README`, но не реализованы в данном трекере. Быстрая ротация при сбоях (fail-fast) ожидается рядом устаревших тестов, но конфликтует с текущим механизмом теневой замены.

**Целевое решение:**

- Отслеживать стабильную идентичность каждого потока (per-flow identity) и его фактический прогресс (forward progress), используя доступные счетчики байт/пакетов; сохранять источник данных и уровень уверенности. Заполненность очереди сокета не тождественна объему переданных байт.
- Не интерпретировать пакеты поддержания связи (idle keepalive), пустые очереди сокетов, штатное закрытие FIN, отсутствие procfs, корректировку системного времени или единичный несвязанный сброс как однозначное вмешательство со стороны DPI.
- Использовать монотонное время для расчета длительности процессов и UTC-время для записей. Корректно обрабатывать усечение/ротацию логов и недоступность procfs без генерации вымышленных событий.
- Поддерживать раздельные политики для подозрений на сброс (reset-cut), зависание потока (stalled-flow) и опциональный детектор эпидемий сбоев; реализовать задокументированный рабочий процесс эпидемий как явную фичу со своими порогами и тестами.
- Генерировать структурированное событие, содержащее кортеж потока (flow tuple), время, длительность, доказательства завершения, счетчики, привязку к слоту, снимок монитора и уровень уверенности. Подавлять дубликаты и обеспечивать независимость сбора диагностических данных от того, включена ли ротация.
- Отдавать приоритет точной атрибуции меток через conntrack и CLI-откату для нее. Помечать неразрешенную атрибуцию и откат к «наиболее активному слоту»; никогда не выдавать последний вариант за точный результат.

### FR-09 — Наблюдаемость трафика и соединений

Сохранять общие показатели и дельты по очередям: байты, пакеты, pps, пропускную способность, активность/долю участия и источник измерений. Текущими источниками являются счетчики цепочек `iptables` и данные очередей `nfnetlink`; при отсутствии данных по байтам используется аппроксимация в 1500 байт на пакет с соответствующей пометкой. Необходимо валидировать реальную семантику полей ядра, прежде чем интерпретировать поле `nfnetlink` как кумулятивный счетчик пакетов.

Сохранять сводные данные по подключенным клиентам Shadowsocks/SOCKS и количество соединений в трекере, но именовать каждую метрику в соответствии с ее реальной областью видимости. Поддерживать парсинг IPv4/IPv6 и счетчики conntrack для оригинального и ответного направлений потока. Не маркировать все HTTPS-сокеты как сессии YouTube, а счетчики уровня очередей — как трафик конкретного потока.

**Целевое решение:** снимать показания счетчиков один раз за фиксированный интервал и публиковать неизменяемые (immutable) снимки состояния. Чтение по HTTP, обогащение логов и решения о ротации не должны сдвигать или сбрасывать общие базовые линии дельт. Включать в снимок метку времени выборки, интервал, единицы измерения, статус устаревания, факт сброса счетчиков и флаги расчетных/недоступных данных.

### FR-10 — Журналы и персистентность (persistence)

**Реализованный активный журнал:** унифицированные JSONL-события `cut`, `idle`, `degraded`, `info`, `test_ok`, `test_fail`, `rotation`; содержит временную метку и контекстную полезную нагрузку; ограничен буфером памяти на 10 000 событий; доступен через API недавних событий. Лог панели пула отдельно хранит до 300 сообщений. Хвосты логов слотов (slot tails) сохраняют до 300 строк.

**Частично реализовано:** детальный регистратор блокировок (cut logger) поддерживает запись/вывод списка/экспорт/очистку и буфер на 500 записей, но не инициализируется текущим сервером. Эндпоинты для блокировок (cuts), описанные в README, отсутствуют. Восстановление оценок вызывает недавние события журнала в памяти после запуска, но инициализация журнала считает строки на диске без загрузки их содержимого, поэтому персистентность фактически не восстанавливает исторические оценки (scores).

**Целевое решение:**

- Единая версионированная схема событий со стабильными ID; скоррелированные блокировки (cuts), зонды, тесты и ротации. Предоставление отфильтрованных недавних записей, курсорная пагинация, экспорт в NDJSON и авторизованная явная очистка.
- Сохранение полного диагностического контекста: поток/слот/стратегия, счетчики и уровень уверенности, состояние монитора, ограниченные хвосты логов панели/воркеров/прокси, а также причины отката. Скрытие конфиденциальных данных (redaction) и настройка хранения для чувствительных эндпоинтов.
- Использование надежной записи в конец файла (append-only), ограниченных очередей/буферов, настраиваемого времени хранения и фактического удаления устаревших бэкапов. Дефолтные базовые настройки предусматривают файлы по 2 МиБ и три бэкапа; текущие циклы ротации могут оставлять один дополнительный устаревший бэкап.
- Восстановление валидных сохраненных событий и/или чекпоинтов при запуске; корректная обработка частично поврежденных или незавершенных финальных строк. Никогда не заявлять молча об успешной персистентности на диске, если запись завершилась ошибкой.
- Явное указание, включает ли экспорт/очистка ротированную историю; дефолтные целевые настройки должны охватывать сохраненную историю запрашиваемого журнала, а не только текущий файл.
- Хранение политики пула и желаемых назначений отдельно от конфигурации движка, вместе с валидированным состоянием скоринга. Текущие настройки UI находятся преимущественно в памяти и не должны ошибочно приниматься за долговременную конфигурацию.

### FR-11 — Разведка ТСПУ (TSPU reconnaissance) и экспорт датасетов

**Частично реализовано / отключено:** существует объемный модуль `TspuIntel`, но текущий запуск сервера не создает его, колбэки блокировок (cut callbacks) его не вызывают, а задокументированные маршруты (routes) для `intel` отсутствуют.

Необходимо сохранить его запланированный асинхронный воркфлоу: зафиксированная блокировка -> ограниченная задача сканирования (probe job) -> независимый датасет JSONL -> скоррелированная сопутствующая запись в журнале. Поддержка ручного одиночного зондирования, статуса, вывода списка, экспорта, очистки, конфигурации среды выполнения, периода охлаждения и ограничения на одну одновременно запущенную задачу. Дефолтные настройки: включен в модуле, 30-секундный кулдаун, номинальный бюджет 1800 мс, максимальный TTL 30, SNI `youtube.com`, режим сухой проверки (dry run) — `false`. Отсутствие реальных возможностей в системе на данный момент активирует детерминированный симулятор; целевая архитектура должна четко помечать его и отделять симулированные датасеты от реальных продакшен-свидетельств.

Блоки датасета, которые необходимо сохранить и версионировать:

| Блок | Обязательное содержимое |
| :--- | :--- |
| `environment` | ASN/имя с указанием источника данных (provenance), классификация типа соединения и целевого хоста, уровень неопределенности. |
| `session_profile` | Время жизни сессии, отправленные/полученные байты, отправленные пакеты, тип завершения; незадействованные счетчики остаются `null`. |
| `tspu_network_metrics` | Оценочный хоп вмешательства, хоп назначения, дельта расстояния, оценка входящего TTL, карта и сводка TTL. |
| `tspu_l7_vulnerabilities` | Результаты split-position 2/5, исходы перекрытия/изменения порядка (overlap/reorder), валидация фейкового TLS/рандома, QUIC/контрольные наблюдения, свидетельства соединения/RST/ServerHello для каждого зонда, уровень уверенности, RTT, фингерпринт RST, аномалии TCP и результаты качества канала. |
| `strategy_context` | Имя стратегии / сырые опции, оценка до события и флаг, была ли оценка известна. |

Метаданные включают версию датасета, ID блокировки, фактически использованные таргет и SNI, UTC-время/день недели, затраченное время, режим, причины частичной/деградировавшей работы и доступность полей контекста.

**Целевые механизмы контроля:** ограничение адресов назначения; ограничение времени жизни DNS, сокетов, снифферов и воркеров единым таймаутом; исключение маркированных диагностических зондов из обработки пулом и обнаружения блокировок; отмена/очистка задач при выключении. Предпочтительно использовать реальные счетчики для конкретного потока, а не агрегированный трафик очереди, приписанный к одной сессии. Разделение целевой ASN и ASN провайдера доступа — текущий поиск использует IP назначения, несмотря на то, что поля названы `isp_*`. Результаты отсутствия ответа, неудачного хэндшейка, отсутствия низкоуровневых возможностей системы и подтвержденные отрицательные исходы зондирования должны оставаться строго раздельными. Валидация протокольных зондов должна быть достаточной для подтверждения заявляемых ими выводов, особенно для QUIC. Механизмы DNS-отката (failover)/кэширования и поиска ASN должны раскрывать источник данных, а не фабриковать личность провайдера.

### FR-12 — Браузерная панель (панель управления)

**Реализовано:** русскоязычный темный дашборд под названием «Ландшафт обхода»; вкладки «Ландшафт» и «Настройки»; отображение стратегий/блокировок/здоровья/соединений в реальном времени; индикаторы пула/монитора; элементы управления включением/выключением/проверкой/добавлением; Canvas-граф атрибутов стратегий, их связей и статусов; масштабирование/сброс/панорамирование, информация при наведении, выбор/детализация, фокус на векторах и отображение оценки/опасности (score/hazard); просмотр активности/событий и очистка логов на стороне клиента; конфигурация пула и детектора; проверка curl URL/порта и превью команд; просмотр сырого конфига; импорт JSON с префиксом; список стратегий.

Текущий опрос (polling): пул/монитор каждые 3 с, трафик каждые 2 с, векторы/лог каждые 4 с, каталог каждые 15 с. Некоторые JavaScript-функции определены дважды (более поздние определения перезаписывают ранние). Текущие визуальные классификации являются эвристическими, а не измеренной топологией сети.

**Целевое решение:** сохранить рабочие процессы оператора, а не точную попиксельную верстку. Добавить доступные альтернативные таблицы, клавиатурную навигацию, адаптивный дизайн, состояния загрузки/ошибки/устаревания данных, явные индикаторы неизвестных/симулированных параметров, обратную связь при персистентном сохранении и подтверждения для деструктивных действий. Открыть через UI рабочие процессы ручной настройки/удаления слотов и редактирования/бэкапа классического режима, которые уже доступны через API. Восстанавливать интерфейсы блокировок/разведки (`cut/intel`) только тогда, когда их бэкенд действительно интегрирован. Очистка на стороне клиента должна быть отделена от удаления журнала на сервере. Экранировать ненадежный текст стратегий/логов; никогда не внедрять его в HTML небезопасным образом. Приостанавливать/снижать частоту опроса и анимации в скрытых вкладках, предотвращать наложение запросов и использовать единую каноническую классификацию сервера.

### FR-13 — Внешние инструменты и расширения

Поддерживается интеграция и сохранение доступа к оригинальным утилитам (`blockcheck2.sh`, `blockcheckw`, `curl`), кастомным скриптам, ресурсам Lua и файлам полезной нагрузки с поддержкой CLI-сканирования (HTTP, TLS, QUIC). Предусмотрены регламенты обслуживания для временной приостановки пула и перехвата трафика во время внешнего сканирования с последующим восстановлением системных состояний. Безопасность обеспечивается исключением автоматического выполнения незащищенных пользовательских скриптов из веб-интерфейса.

## 5. Реестр совместимости API

Основные маршруты, реализованные в `...\panel\server.py`, подлежат адаптации, стандартизации кодов ошибок (400, 401, 403, 404, 409, 413, 422, 503) и строгой валидации. Деструктивные действия переведены на методы POST/DELETE, а долгие задачи используют асинхронные Job ID.

* **Основные GET-маршруты:** `/`, `/api/config`, `/api/strategies`, `/api/connections`, `/api/pool/status`, `/api/pool/log`, `/api/pool/vectors`, `/api/pool/traffic`, `/api/monitor/status`, `/api/tspu-log`.
* **Основные POST-маршруты:** `/api/apply`, `/api/pool/enable`, `/api/pool/configure`, `/api/pool/slot/set`, `/api/pool/slot/add`, `/api/pool/slot/remove`, `/api/pool/check`, `/api/monitor/configure`, `/api/save-nfqws`, `/api/restart`, `/api/test-curl`, `/api/import-json`, `/api/backup`.
* Полная таблица маршрутов и параметры конфигурации доступны в исходной технической документации.

**Задокументированы, но отсутствуют:**
* `GET /api/cuts`, `GET /api/cuts/export`, `POST /api/cuts/clear`
* `GET /api/intel/status`, `GET /api/intel/list?limit=50`, `GET /api/intel/export`, `GET /api/intel/clear`, `POST /api/intel/probe`

**Целевые дополнения:** реализация недостающих процессов `cuts` и `intel`, внедрение аутентификации, версионируемых схем API и строгой обработки статусов ошибок без ложных подтверждений успеха.

## 6. Контракт конфигурации и хранения данных

Раздел описывает параметры конфигурации (порты `SS_PORT`, `SOCKS_PORT`, секреты `SS_PASSWORD`, таймауты, метки `DESYNC_MARK`, параметры логирования и модуля `intel`) и требования к их преемственности, валидации и изоляции внутри контейнера. Требуется сохранять абсолютные пути к данным (`/opt/zapret2/config`, `/opt/zapret2/strategies`, `/opt/zapret2/logs` и др.), обеспечивать сквозную передачу апстрим-параметров и запрещать перезапись рабочих конфигов дефолтными без подтверждения миграции.
